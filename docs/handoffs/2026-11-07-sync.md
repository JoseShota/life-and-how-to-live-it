## Problems in the current code that the old sync notes (02-ARCHITECTURE, prompts/P2-sync.md) miss
Verify each yourself; the code is the source of truth.
1. **XP ledger ids are random** (`award()` in `src/game/engine.ts:17`, plus direct `db.xp.add` in `achievements.ts:95,121`, `engine.ts:255,275,639`). If both devices grade the same day, "union by id" doubles every award. And `revoke()` deletes rows physically, so a revoke never reaches the other device. Most refIds are already deterministic (`workday:<date>`, `habit:<habitId>:<date>`, `session:<id>`, `ach:<key>`, `wl:<n>`, `shield:use:…`, `review:<monday>`); check `redeem` and any refId built from `uid()`.
2. **Seeded rows differ per device.** `seedIfEmpty()` (`src/db/seed.ts:89–96`) gives areas, tasks, habits, accounts, rewards, goals and opportunities random ids on each device. A naive first sync duplicates them, and `habits` has a unique `&key` index, so the pull would throw.
3. **Derived state.** `evaluateDay()` recomputes the habit logs, focus XP, bonuses, grades, shields, the weekly scorecard and achievements from inputs. After pulling inputs (sessions, habit logs, settings like `workTargets`/`teachingSchedule`), the touched days must be re-evaluated so both devices converge.
4. **About 70 write call sites** (`db.<table>.add/put/update/delete/bulk*/modify`). Changing every one to a write helper (as P2-2 suggests) is a large, risky diff. Dexie hooks or a DBCore middleware can stamp `updatedAt` and record deletes centrally.
5. **Device-local state.** `activeTimer`, `lastBackupAt` and `showMarquee` should not sync. Import (replaces all data) and "Reset app" (`db.delete()`) need defined behaviour once sync exists: a reset must not wipe the cloud, and an import must not be silently overwritten by the next pull.
6. **Seeding after a wipe.** A device that replaces its data with the cloud copy must not run `seedIfEmpty()` between the wipe and the pull.

## Design proposed to the user (not approved yet; improve it if you see better)
- **Supabase** (as planned in 02-ARCHITECTURE; it will also host the AI coach), email magic-link auth.
- **End-to-end encrypted, one generic table**: `records(user_id, tbl, id, updated_at, deleted_at, seq, data)`, where `data` is the row encrypted on the device (WebCrypto AES-GCM, key derived from a passphrase with PBKDF2 or similar). RLS: `user_id = auth.uid()`. The server can't read money or schedule data (fits the privacy rule), and Dexie schema changes need no server migration. Trade-off: a forgotten passphrase makes the cloud copy unreadable (the devices and backups still have the data). The anon key in the frontend is fine: it is public by design, and RLS protects the rows.
- **Change tracking without touching the call sites**: hooks/middleware stamp `updatedAt` on create/update and record deletes in a local `tombstones` table. Reads stay unchanged. Writes applied from a pull must bypass the hooks.
- **Deterministic XP ids** (id derived from `refId`) in a new Dexie version, with an `upgrade()` that rewrites existing rows and a migration test.
- **Sync loop**: push local changes since the last push; pull by a server-assigned sequence (`seq`, so device clock skew can't hide rows); last-write-wins per row by `updatedAt`; tombstones apply deletes. Settings sync per key, except the device-local keys. Re-evaluate touched days after a pull.
- **Triggers**: app open/focus, every 60 s while visible, 3 s after a local write. A small cloud glyph in the HUD shows synced, syncing, offline or error (hand-drawn glyph, no icon library, "Thermae" style; see 08-DESIGN-SYSTEM).
- **First sync**: one device uploads. The other device auto-exports a backup, then replaces its data with the cloud copy. No merge of two histories unless the user asks for it.
- **Dependency**: `@supabase/supabase-js`, exact version, lazy-loaded (justify it in one line in the commit). Plain `fetch` against PostgREST/GoTrue is an alternative if it's much smaller; your call, explain it.

**Proposed commits**: (1) change tracking, tombstones and deterministic XP ids (new Dexie version, no network); (2) encryption and the sync engine behind an interface, tested with two simulated clients (fake-indexeddb) against an in-memory fake server: create on A, edit on B, delete on A, concurrent edits, offline then reconnect, XP not doubled, derived XP converges; (3) Supabase SQL in `supabase/migrations/`, the client, sign-in in Control, the status glyph, and `.env.example`; (4) the first-sync flow.
